# After Phase 17 — D-146: the owner adds and edits barbers, each with a login made at once; no walk-ins for the owner

**Status:** [x] (Session 27, 2026-11-18) · requested by the user after D-145 · decision: D-146

## The request (user, Session 27)
- Remove the page `/shop/walk-in` from the shop owner.
- The shop owner has full control to add and edit barbers.
- When a barber is created, a login is made automatically with a random password that the owner gives to the barber; the barber changes it at the first sign-in.

## Defaults stated to the user (not asked)
- Walk-ins stay the barbers' (D-145); the owner loses them in the API too, not only the page (D-134's precedent).
- "Full control" = add, edit the profile, photo, WhatsApp number (also the sign-in), the services the barber does, turn the login on/off or renew its password, disable/enable. Not: delete (booking history; disable instead), move to another shop (D-011), see the number unmasked.
- The mobile is required when the owner adds a barber (it is the sign-in); it can be changed, not removed.
- Every barber temporary password is generated by the server, also for the admin's «تفعيل الدخول»; the admin's own create is unchanged (no login until turned on).
- Plan limits (`MaxProfessionals`) are not enforced (they never were); mentioned to the user.

## Design (advisor-reviewed)
- **Tenancy.** Separate shop handlers on `ICurrentTenant`/the tenant filter (the admin data scope may only be used in `Application.Admin`, TenancyRules). The create takes no shop id. Another shop's barber → 404 on every endpoint.
- **Uniqueness across shops.** The owner's `AnyAsync` on the contacts sees one shop; the unique indexes (`ix_professional_contacts_whatsapp_lookup_hash`, `ix_users_login_phone_hash`) see all, so `ProfessionalSupport.SaveAsync` maps a unique violation on either to `validation.whatsapp_taken`.
- **Ordering.** One transaction: save the professional and its contact, then `IBarberLoginSync.CreateAsync` (Identity, through a BuildingBlocks port; `UserManager.CreateAsync` saves on the shared context), then save the login's audit entry, then commit. Any failure leaves without committing.
- **Password hygiene.** `TemporaryPasswords.New()` (CSPRNG, 12 of 31 characters, no look-alikes); answered once; `ToString` overrides on the records that carry it or a number; no-store; never in a URL (the create form shows the dialog first, then opens the barber's page).
- **Walk-ins.** `ShopOwner` = shop permissions minus `Shop.Bookings.CreateWalkIn`; the nav item and tab bar follow the permission; the bar gets `barbers` after `walkIn` so each role still has four tabs.

## API contracts and UI routes
| Route | Who | What |
|---|---|---|
| `POST /api/v1/shop/professionals` | owner (`Shop.Barbers.Manage`) | `{ nameAr, nameEn, specialtyAr?, specialtyEn?, bioAr?, bioEn?, whatsAppNumber, notificationsEnabled }` → 201 `{ barber, temporaryPassword }` |
| `GET`/`PUT /api/v1/shop/professionals/{id}` | owner | `ShopBarberResponse` (number masked) / profile edit with `version` |
| `PUT /api/v1/shop/professionals/{id}/whatsapp` | owner | `{ whatsAppNumber, notificationsEnabled, keepCurrentNumber }`; the number is required unless kept |
| `POST /api/v1/shop/professionals/{id}/disable`, `…/enable` | owner | status; disabling turns the login off |
| `PUT`/`DELETE /api/v1/shop/professionals/{id}/avatar` | owner | photo |
| `GET`/`PUT /api/v1/shop/professionals/{id}/services` | owner | the shop's services and which the barber does |
| `PUT /api/v1/shop/professionals/{id}/login`, `PUT /api/v1/admin/professionals/{id}/login` | owner / admin | no body → `{ login, temporaryPassword }` |
| `/shop/barbers`, `/shop/barbers/new`, `/shop/barbers/{id}` | owner | list, add, the barber's page |
| `/shop/walk-in` | barbers only | the owner sees «no access» |
